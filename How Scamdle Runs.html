How Scamdle runs

Everything we've set up so far, in plain words. You don't need any experience with websites to follow this. Read it once from top to bottom; it takes about ten minutes.

Written for the Scamdle team · state as of 28 October 2026

The short version

We use three tools. Each one has exactly one job, so you always know where something belongs.

Notion

Where we think and keep track. Your journal (including your hours), your ideas and questions, research, scam screenshots, meeting notes.

You'll use it every week.

GitHub

Where we plan the work and keep the code. Every task is an "issue" with an owner and a week. The board shows them all.

You'll use it every time you work on a task.

Vercel

Where the website lives on the internet. It builds the site automatically from the code in GitHub, so we never upload anything by hand.

You'll mostly see it as a link on your pull request.

A simple rule decides between Notion and GitHub: if someone has to do it, it's a GitHub issue. If it's a thought, a finding or a question, it goes in your Notion journal.

How a task gets from idea to website

This is the path every change takes, whether it's a new page, a fix or one word in the README. The filled circles are things you do; the rest happens automatically or is done by a reviewer.

  1. Pick up your issueOn the board, open your team's view or filter by your name. Each issue has a week (W3, W4…) and a size: S is up to 2 hours, M up to 5.
  2. Make a branchA branch is your own private copy of the code to work in. Nothing you do there affects anyone else until it's merged.
  3. Make your change, commit, pushA commit is a saved step with a short note. Pushing sends your branch to GitHub.
  4. Open a pull request (PR)A PR says "here's my change, please check it and add it to the real thing". Write in it what you did and which issue it closes, for example "Closes #23".
  5. Automatic checks runGitHub checks the code for mistakes (lint, typecheck, tests). Vercel builds a preview of the site with your change. Both need a green ✅.
  6. Click through your previewThe Vercel bot posts a "Visit Preview" link on your PR. Open it, ideally on a phone too, and check your change really works. Paste the link in the PR description.
  7. Someone reviews and approvesJasper or Gijs is asked automatically. You can't approve your own PR; nobody can.
  8. Jasper or Gijs mergesOnly they can add changes to main, the version that runs the real website. Nobody can push to main directly, them included.
  9. The real website updatesAbout a minute after the merge, Vercel builds main and replaces the live site. If something goes badly wrong, Vercel can put the previous version back in seconds.

New to branches and pull requests? docs/how-we-work.md in the repository walks through one whole task with pictures.

What the app is made of

The app is one project that holds both the website and the tools to manage its content. You'll hear these words a lot:

Next.js
The framework that makes the website: the pages players see. The house.
Payload
A content management system (CMS) built into the same project. It gives us an admin panel, logins and a way to store exercises without building any of that ourselves. The back office.
/admin
The admin panel, at the website address plus /admin. The team logs in here to write exercises, upload screenshots and manage accounts. No coding needed. Players never see it.
Exercises
Each exercise has a title, a category (email, links, messages, fake screens, AI media), a format (spot the red flags, real or fake, what would you do next) and a status: Draft → In review → Published. Only published exercises are visible to the public. The exact format of an exercise is still being decided in issue #15.
/api
The same data in raw form for computers, at the website address plus /api. For example /api/exercises lists exercises. The website itself mostly fetches its data internally and doesn't go through this.
Database (Neon)
Where everything is stored: accounts, exercises and later every answer players give. It runs on a service called Neon, in Frankfurt. The filing cabinet.
Migration
A small file that describes a change to how the database is organised, for example "exercises now have a difficulty field". Migrations make sure every copy of the database changes the same way. Vercel applies them automatically when it builds the site.
Tailwind
The styling system for the pages: colours, sizes and spacing, written as short class names in the code.
Checks (CI)
Automatic tests that run on every pull request: lint spots sloppy code, typecheck spots mix-ups like text where a number belongs, and tests check that our logic gives the right answers.

Five rules

Please don't skip these

  • Don't run the app on your laptop yet. Until #173 is done, the local setup would point at the real database.
  • Never post passwords, database addresses or .env files in Discord, Notion or GitHub. The repository is public.
  • Never change the database by hand. Changing an exercise field means writing a migration (ask in your journal if unsure).
  • Remove names, phone numbers and account details from real scam screenshots before saving them anywhere.
  • Check your own preview before asking for a review.
